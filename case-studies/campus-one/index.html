FLAGSHIP CASE STUDY · MOBILE / WEB / BACKEND

Campus One

把分散的課程、校務、訊息、地圖與學習資訊整理成「現在下一步要做什麼」。這個專案的重點不是功能數量，而是 Mobile、Web、Backend、角色權限、資料邊界與驗證方式能不能接成同一套產品。

查看 GitHub Repo 2-minute reviewer path
WHY THIS EXISTS

問題不是入口太少，
而是資訊彼此不連續。

01

上下文分散

課表、公告、LMS、群組訊息與校園服務各自存在，使用者要自己拼出今天的優先順序。

02

角色不同

學生、教師、職員與管理者不能只換首頁文案；入口、資料可見範圍與可執行動作都不同。

03

服務會失效

外部 LMS、交通、校務或 AI provider 不保證永遠可用，產品需要 degraded path，而不是一斷線就整個失效。

SYSTEM SHAPE

跨端不是把三個資料夾
放在同一個 repo。

ROLE MODEL

入口只是第一層，
權限必須一路走到底。

Student課程 / 作業 / 學習行動
Teacher教學 / 點名 / 評量
Staff校園服務與工單
Dept. Head審核與部門資料
Admin全校設定與管理
Tab先限制主要入口

UI permission隱藏不該執行的操作
Backend authz敏感操作不信任 client

ENGINEERING PROOF

不是用「完整」形容，
而是讓 reviewer 自己驗。

Expo + Next.jsMobile / Web 兩個主要 client surface
FirebaseFunctions + Firestore + Storage rules
Shared TS共用 contract 與角色規則
Unit + RulesMobile、Web、Functions、security rules 分開驗證
Maestro E2EUI flow 與 unit tests 分離
CI gateslint、typecheck、security、build 與測試不是同一個模糊 job
AI BOUNDARY

AI 是一層，
不是資料權威。

可以做

  • 整理與摘要
  • 依授權上下文提供建議
  • 產生下一步候選動作
  • 在低風險流程中協助導航與草稿

不能假設

  • 直接讀所有使用者資料
  • 跳過角色與資料權限
  • 把高敏感 action 直接寫入
  • 把模型回答當校務資料來源
REVIEW PATH

兩分鐘內就能判斷
這個 repo 做到哪裡。

README：先理解產品與 monorepo 範圍
Mobile demo：確認實際 UI，不看概念稿
Role + data flow：確認權限不是只有前端按鈕
CI workflow：確認驗證面與 failure boundaries
AI architecture：確認 AI 的資料與 action 邊界
「如果只有兩分鐘，我希望作品本身能證明它不是一組畫面，而是一套有邊界、有失敗情境、也有驗證方法的系統。」Campus One review principle
BOUNDARIES

沒有把 demo 說成
正式校務系統。

目前可檢查

  • Mobile / Web / Backend monorepo
  • 角色與導航邏輯
  • Firebase rules 與 backend boundary
  • 測試、CI 與 E2E workflow
  • repo 內實際 Mobile 截圖

明確不宣稱

  • 正式接管校務權威資料
  • 所有外部服務已正式部署
  • 所有願景功能都已完整落地
  • AI provider 在任何裝置都同樣可用
  • demo data 等於真實校園營運資料
