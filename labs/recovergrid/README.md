# Recovergrid

災難復原不只是「有沒有備份」，還要問：事故發生當下能不能用、資料落差有多大、還原時間是否符合目標。

[操作工作台](https://miiduoa.github.io/labs/recovergrid/) · [核心程式](core.mjs) · [測試](core.test.mjs)

## 檢查方式

使用 Node.js 22 或更新版本：

```sh
node --test labs/recovergrid/core.test.mjs
```

由網站根目錄執行。使用一般狀況與「區域失效」、「備份損毀」、「目標過緊」做對照；可直接修改 RPO、RTO 與決策時間，比較兩種選點優先序。

## 規則與設計取捨

1. 每份備份都要通過基本資格：資料擷取不得晚於事故、備份完成時間不得晚於事故、資料時間不能倒置、來源區域可讀、且標記為已通過完整性檢查。
2. 先排除不可用的還原點，再依政策選擇：`freshest` 優先最小資料落差；`fastest` 優先最短恢復時間。依次以另一指標與 id 穩定排序。
3. RPO 是事故時間減資料擷取時間。RTO 是決策、傳輸、還原、驗證四個估計值總和。目標門檻使用包含等於的比較。
4. 資料不存在、驗證缺失或全部落在失效區域時，必須回報「無法還原」，不能套用錯誤的成功指標。

所有輸入是固定的合成情境，不含真實營運資料。備份的 integrity flag 是外部前提，並未實際重算雜湊或演練資料庫復原；模型亦未考量平行復原、跨區網路壅塞、相依服務與人員調度。不能拿本頁數字充當實際 RTO/RPO 承諾。
